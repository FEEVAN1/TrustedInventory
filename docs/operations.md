## Alerts that block stock (OPS-001)

A ledger reconciliation mismatch or an audit-chain verification failure raises a High alert and blocks
stock mutations on the affected buckets / tenant stream until an operator completes the audited repair
procedure. Never repair a balance with an unexplained direct update (STK-004). In M1 the audit-chain
alert is raised; blocking stock mutations arrives with the ledger in M2.

## Runbooks

### Deployment and rollback (draft)
1. Build images from a tagged commit; restores run in locked mode, so a lock-file drift fails the build.
2. Run the migrator (`TrustedInventory.Migrator migrate`) with the migration identity **before** new API or
   worker instances start. It applies pending scripts in order and refuses to run if an applied script was
   edited (checksum mismatch).
3. Start new API instances; they report ready only when `/health/ready` sees the required schema version.
4. Roll back by redeploying the previous images. Migrations are expand-only within a release
   (docs/migration-design.md §3), so the previous version runs against the newer schema. Never roll back a
   migration by hand.

### Migration recovery (draft)
- **Script failed:** each script runs in its own transaction, so nothing from it is applied and
  `ti.schema_migration` has no row for it. Fix forward with a corrected script under a new number if the
  failed one was already released; otherwise correct it before release.
- **Checksum mismatch:** an applied script was edited. Restore the released file from version control; put
  the change in a new migration.
- **Concurrent migrators:** an advisory lock serialises them; a second instance waits.

### Audit-chain verification failure (draft)
1. A High `AuditChainFailure` alert opens (from `POST /audit/verify` or the daily check).
2. Preserve evidence: snapshot the database and the external checkpoint files before any change.
3. Identify the first failing sequence (the verify response lists `HashMismatch` / `SequenceGap`).
4. Compare with the last signed checkpoint at or before that sequence; rows after it are suspect.
5. Treat as a security incident: rows cannot be changed by the application role, so a mismatch means
   privileged database access. Repair only through an audited operator procedure; never rewrite history.

### Reservation expiry and dispatch blocks (draft, M3)
- The worker's `ReservationExpiry` job (every `Worker:ReservationExpiryIntervalSeconds`, default 60) releases
  unpicked reservations 24 h after allocation (STK-008, DEC-055). Picked stock never expires; part-picked tasks
  keep their picked part. Expired orders drop back to `Confirmed` or `PartAllocated` and can be allocated again.
- A dispatch that returns `409 STOCK_BLOCKED` with `affectedPicks` posted nothing. Each affected pick has one open
  `Rework` task at its staging bin. Either clear the cause (quality hold released, alert closed) and dispatch
  again, or unpick the staged stock to a compatible storage bin with a reason; both complete the task.
- An expired lot cannot ship from its expiry day on (warehouse time zone): unpick it and deallocate the line.

### Counts, exports and attachments (draft, M4)
- A count locks its bins from start until it is posted or cancelled; every stock movement in a locked bin returns
  `409 COUNT_LOCKED` (DEC-059). A stuck count is released by cancelling it with a reason, which keeps every observation.
- Configuration: `Storage:Directory` (the **simulated** object store shared by API and worker) and `Storage:LinkKey`
  (base64, at least 32 bytes, from the secret store; `TI_LINK_KEY` in development). Both are required at startup.
- Exports are queued by the API and generated by the worker's `ExportGeneration` job (every `Worker:ExportIntervalSeconds`,
  default 15). A failed export records its reason; request a new one after fixing the cause. Files are kept 30 days
  (owner decision D05). Download links expire after 15 minutes and work only for the user who requested them.
- Attachments are scanned by a **simulator** at upload; only `Clean` files can be downloaded (DEC-061).

### Billing webhooks (draft, S2; simulator only)
- Configuration: `Billing:Simulator:SigningSecret` (at least 32 characters; optional `Billing:Simulator:PreviousSigningSecret`
  during rotation) and `Billing:InboxKey` (base64, 32 bytes). `TI_BILLING_SIM_SECRET` and `TI_INBOX_KEY` in development; both
  the API and the worker refuse to start without them (DEC-064).
- `POST /api/v1/webhooks/billing/simulator` stores the verified event and answers 200; the worker's `BillingEventJob`
  (every `Worker:BillingEventIntervalSeconds`, default 5) applies it. Billing notices reach tenant outboxes through
  `BillingNoticeRelayJob` (`Worker:BillingNoticeIntervalSeconds`, default 30).
- `Quarantined` events name a reference we do not hold or mix two tenants' references; each opens a
  `cp.billing_task`. Nothing is applied: resolve the task, never edit the payload.
- `Failed` events retry with backoff up to 10 attempts; `last_error` holds the exception type only. A row at 10 attempts
  needs an operator (console and `WebhookBacklog` alert arrive with S2 slice 5).

### Plan changes and cancellation (draft, S2; simulator only)
- A change is effective at the current period end. `PlanChangeJob` (`Worker:PlanChangeIntervalSeconds`, default 60) applies
  it, blocks it (usage or medical stock rose: the owner gets a `PlanChangeBlocked` notice) or, for an upgrade, waits for the
  paid invoice of the new period (DEC-065). A blocked change is never forced: the tenant reduces usage and requests it again.
- A change left `Pending` (provider unreachable when it was requested) completes when the same request is retried.
- Cancellation keeps all data. Access becomes billing-restricted at period end by computation; the provider's end event
  later sets the subscription `Cancelled`.

### Stuck outbox (draft)
- **Symptoms:** rising outbox age, or `OutboxDeadLetter` alerts.
- Leases expire on their own: a crashed worker's batch is picked up by another after `lease_expires_at`.
- A dead-lettered event (10 failed attempts) stays in `ti.outbox_event` with `dead_lettered_at` and
  `last_error`. Fix the cause, then replay by clearing `dead_lettered_at` and resetting `attempts` and
  `next_attempt_at` through an audited operator procedure. Consumers deduplicate on `event_id`, so a
  replay is safe.

### Tenant suspension (draft; replaced by the v3.0 lifecycle matrix)
- A platform administrator suspends or reactivates a tenant through `/platform/tenants/{id}/suspend` and
  `/reactivate`. Both are audited in the tenant's own chain.
- While suspended, tenant users can read but every mutation returns 403.
- Spec v3.0 section 26 replaces this with reason-specific restrictions (billing versus security). This
  runbook is rewritten in S3.
